# FinOps Cost Optimization: Environment-Specific Topologies

To guarantee maximum cost savings in Dev/Test environments while delivering high availability and failure tolerance in Production, the migration pipeline implements **Environment-Specific Topologies**. 

All cost-saving and sizing assumptions are codified as configurable variables, enabling you to customize VM sizes, node counts, and backup states at any time.

---

## 1. Topologies & Sizing Assumptions

The following profiles represent the defaults generated by the Developer agent:

| Parameter | Dev / Test Environment | Production Environment | Cost Rationale |
| :--- | :--- | :--- | :--- |
| **AKS VM SKU** | `Standard_B2s` or `Standard_D2s_v5` | `Standard_D4s_v5` or `Standard_E4s_v5` | B-series offers burstable compute for intermittent non-prod testing. |
| **AKS Node Count** | Min: 1, Max: 2 (Single-node default) | Min: 3, Max: 10 (Multi-AZ distribution) | Eliminates idle system compute overhead in Dev. |
| **Spot Node Pools** | None | Enabled (for batch / stateless pods) | Spot nodes save up to 80% on compute for scale-out pools. |
| **AKS Schedule** | Auto Start/Stop enabled (10h/day) | Always On (100% SLA) | Shutting down Dev on weekends/nights saves ~60% monthly. |
| **Registry SKU** | Basic (local redundancy) | Premium (geo-replication, zone-redundancy) | Premium provides local region high throughput and HA. |
| **Key Vault SKU** | Standard | Premium (HSM protection enabled) | Standard is fully functional; Premium is reserved for hardware keys. |
| **Storage Account** | LRS (Locally Redundant) | GZRS (Geo-Zone-Redundant Storage) | Dev only needs local durability; Prod requires recovery durability. |

## 2. Codified Configuration Template (`variables.tf`)

These values are fully exposed in the root environment directories (e.g. `environments/dev/terraform.tfvars` and `environments/prod/terraform.tfvars`) so they can be modified dynamically:

```hcl
# --- environments/dev/terraform.tfvars ---
environment_name      = "dev"
vm_size               = "Standard_B2s"
system_node_count     = 1
enable_cluster_sleep  = true # Triggers AKS start/stop schedules
acr_sku               = "Basic"
storage_redundancy    = "LRS"
spot_pool_enabled     = false

# --- environments/prod/terraform.tfvars ---
environment_name      = "prod"
vm_size               = "Standard_D4s_v5"
system_node_count     = 3
enable_cluster_sleep  = false
acr_sku               = "Premium"
storage_redundancy    = "GZRS"
spot_pool_enabled     = true
```

## 3. Implementing AKS Start/Stop Schedules

Azure supports stopping and starting AKS clusters dynamically to preserve compute charges. The Developer agent implements this automation via resource schedules.

```hcl
# Stops the AKS cluster during off-hours (e.g. 8 PM to 8 AM UTC) in Dev
resource "azurerm_resource_group_template_deployment" "aks_sleep_schedule" {
  count               = var.enable_cluster_sleep ? 1 : 0
  name                = "aks-sleep-schedule-dev"
  resource_group_name = var.resource_group_name
  deployment_mode     = "Incremental"

  # Uses standard ARM template scheduler
  template_content = <<TEMPLATE
  {
    "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#",
    "contentVersion": "1.0.0.0",
    "resources": [
      {
        "type": "Microsoft.DevTestLab/schedules",
        "apiVersion": "2018-09-15",
        "name": "[concat('shutdown-computelab-', '${var.cluster_name}')]",
        "location": "${var.location}",
        "properties": {
          "status": "Enabled",
          "taskType": "ComputationLabStopTask",
          "dailyRecurrence": {
            "time": "2000"
          },
          "timeZoneId": "UTC",
          "targetResourceId": "${var.aks_cluster_id}"
        }
      }
    ]
  }
  TEMPLATE
}
```

## 4. How to Update Sizing Policies

1. **Locate variables:** Navigate to the specific repository's `environments/<env>/terraform.tfvars` file.
2. **Modify parameters:** Update `vm_size`, `system_node_count`, or `storage_redundancy` to your desired Azure sizes.
3. **Re-plan:** Execute `terraform plan` to apply updates dynamically.

## 5. Mandatory Cost-Attribution Tagging Schema

To support automated cost allocation, telemetry, and corporate financial auditing, all billable Azure resources MUST be tagged with the mandatory tagging schema specified in `migration-config.json`.

### Tag Specification

| Tag Key | Expected Value | Audit Purpose |
| :--- | :--- | :--- |
| **`Environment`** | `${var.environment_name}` (e.g., `dev`, `test`, `prod`) | Allocates costs to the proper environment lifecycle budget. |
| **`MigrationSource`** | Original AWS ARN / Name (e.g., `arn:aws:rds:...` or `my-vpc-id`) | Facilitates pre/post migration cost reconciliation and source tracking. |
| **`CostCenter`** | Cost center ID (e.g., `CC-999-DEVOPS`) | Identifies the department or business unit responsible for funding. |
| **`Orchestrator`** | `Antigravity-Migration-Factory` | Identifies resources provisioned by the agentic migration engine. |

### Implementation Example in Terraform

```hcl
resource "azurerm_resource_group" "rg" {
  name     = "rg-${var.environment_name}-migrated"
  location = var.location

  tags = {
    Environment     = var.environment_name
    MigrationSource = "arn:aws:ec2:us-east-1:123456789012:vpc/vpc-0123456789abcdef0"
    CostCenter      = "CC-999-DEVOPS"
    Orchestrator    = "Antigravity-Migration-Factory"
  }
}
```

### Audit Enforcement & Compliance
- **Real-time Audits:** The Cost Estimator agent automatically scans generated resources to verify the presence of all 4 required tags. Any resource missing these tags will be flagged as a cost anomaly and trigger a build failure.
- **Enterprise Reports:** Tag compliance is ingested daily by the automated cost allocation billing engine. Non-compliant resources are automatically flagged for quarantine or termination schedules.
